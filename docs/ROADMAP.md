# 天文与航天开发路线

以下是规划，不代表已经实现。先把每个阶段做成可玩的闭环，再增加天体和载具数量。具体天体、美术风格、科技节奏由后续需求决定。

## 1. 地面天文观测

从手持望远镜扩展到观测站：选择目标、检查维度/天气/时间/天空遮挡、记录观测成果。天体目录与探索进度分开设计，便于以后增加新的行星和探测目标。若使用现实星空，要先约定游戏时间、方位和真实天文时间的对应关系。

建议按用途引入 `astronomy/` 与 `observation/` 包。每次观测由服务端验证条件；客户端负责交互与显示。玩家研究成果可用带持久化/同步策略的 attachment，团队或世界共享成果可用 SavedData；先确定数据归属再选择实现。

验收：可以识别至少一个天体；不满足条件时给出原因；退出重进保留成果；多人之间的数据归属明确。

## 2. 卫星探测

为卫星核心增加组装、任务选择、发射和探测结果回收。首版可以抽象任务和运行时间，无需一开始模拟真实轨道动力学。

建议引入 `satellite/`，定义稳定任务 ID、状态转换与存档格式。任务只能由服务端推进；重启、区块卸载和玩家离线不应意外复制奖励或丢失任务。

验收：一次任务完整经过准备、发射、运行和回收；存档重载后可以继续；同一成果不能重复领取。

## 3. 火箭与发射设施

逐步加入发射台结构检查、载人火箭实体、燃料/能量、倒计时、安全登乘和目的地选择。先实现一个火箭型号与一个目标。

建议引入 `rocket/` 与 `network/`；网络消息使用 1.21.1 NeoForge payload API。服务端验证乘员、目的地解锁、燃料、发射台和发射状态；只在状态确认后消耗资源。明确取消、断线、死亡和服务器重启时的处理方式。

验收：玩家能登乘并完成一次发射；重复消息不重复消耗资源或生成载具；多人旁观与乘坐状态一致。

## 4. 星球维度与生存

先完成一个月球式目的地：维度类型、地形与群系、安全落点、返航流程；再加入重力、氧气、温度、辐射和基地建设。具体采用月球、火星或虚构天体仍可调整。

建议引入 `planet/` 与 `worldgen/`，通过数据驱动的天体定义关联维度和探索条件。维度传送使用 1.21.1 API，明确载具、乘员、区块加载和安全落点处理。不要将瞬间传送描述为已实现连续航天飞行。

验收：能够发射、抵达、落地并返回；重载存档后维度和进度稳定；专用服务器多人往返正常。

## 设计边界

- 当前模板没有对 Galacticraft 的运行依赖；参考其玩法主题，保持独立命名和实现。
- 保持 Minecraft 1.21.1 与 NeoForge API 的版本一致；后续 1.21.x 的物品模型、数据组件和网络示例可能不兼容。
- 等实际行为需要时再增加 GUI、网络、实体、持久化或外部依赖，避免先建大量空壳框架。
- 渲染、按键和屏幕放在独立客户端入口；世界规则、任务和存档归服务端管理。
